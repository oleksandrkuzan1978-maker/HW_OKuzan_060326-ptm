ОТЧЕТ о проделанных работах по устранению проблемы при подключении
к IP-адресу 35.159.74.144. Дата проведения работ: 23.06.2026
Автор отчета: Александр Кузан, группа 060326-ptm.

При попытке подключения к хосту 35.159.74.144 на экране выдается сообщение:
"$wgServer must be set in LocalSettings.php. See https://www.mediawiki.org/..."

В файле конфигурации LocalSettings.php есть проблемы, связанные с переменной
$wgServer (переменная имени сервера). Нужно найти эту переменную и исправить.
Известно, что есть backup этого файла (LocalSettings (5).php), на сервере
работает web-сервер и функционирует веб-приложение.

1. Подключаемся к серверу:
   ssh -i ~/.ssh/ich.pem ec2-user@35.159.74.144
   (Пояснение: подключиться к серверу 35.159.74.144 под пользователем
   ec2-user, используя SSH-ключ в файле ~/.ssh/ich.pem. Ключ -i указывает
   для SSH, какой приватный ключ использовать для входа.)

2. Смотрим статус процесса httpd:
   sudo service httpd status
   (Пояснение: sudo — запуск с правами администратора; service — утилита
   для управления службами; httpd — служба веб-сервера Apache; status —
   показать текущее состояние.)

   При выводе в строке Active показано active (running). Это говорит о том,
   что веб-сервис httpd активен и запущен. Однако после остановки сервиса
   командой "sudo service httpd stop", сервис не запускается стандартной
   командой "sudo service httpd start".

3. Для восстановления файла LocalSettings.php пытаемся скопировать его
   бекап-копию LocalSettings (5).php в папку /var/www/html/mediawiki/.
   Команда:
   cp /home/ec2-user/LocalSettings\ \(5\).php /var/www/html/mediawiki/LocalSettings.php
   При попытке копирования на экране выдается сообщение об ошибке:
   «cp: failed to extend '...': No space left on device» (Нет места).

4. Проверяем количество свободного места на диске командой:
   df -h
   В разделе диска /dev/nbme0n1p1 (размер 10G) занято 100% места.

5. При помощи команды:
   sudo find / -type f -size +120M
   ищем на диске файлы размером больше 120 Мб. Обнаружено два файла:
   - /var/log/httpd/log_20260622.tar.gz (494 Мб)
   - /var/log/httpd/access_log-20260622 (7 Гб) — специальный лог-файл
     для записи всех запросов пользователей сервиса.

6. Для освобождения места на диске удаляем огромный лог-файл:
   sudo rm -rf /var/log/httpd/access_log-20260622

7. Копируем файл LocalSettings.php в нужное место:
   cp LocalSettings.php\ \(5\).php /var/www/html/mediawiki/LocalSettings.php
   Вновь запускаем httpd-сервис командой:
   sudo service httpd start
   Сервис успешно запущен. Вероятно, причиной неудачных попыток
   перезапуска сервиса ранее было полное отсутствие места на диске.

8. После внесения изменений выполнена повторная проверка подключения
   по IP-адресу 35.159.74.144. Но система перенаправляет на другой
   IP-адрес: 18.153.51.162. Проведен анализ файла LocalSettings.php,
   так как в начале, при попытке зайти на сайт, сообщалось 
   о проблеме с переменной  $wgServer в этом файле. 
   Обнаружено, что переменной $wgServer присвоено значение
   «https://18.153.51.162», хотя должно быть: «http://35.159.74.144».

   Это произошло из-за того, что на Амазоне нет фиксированного IP.
   Публичный адрес сервера меняется при остановке и запуске самого
   сервера, если не используется Elastic IP. Прописываем правильный
   IP-адрес http://35.159.74.144 и перезапускаем веб-сервер:
   sudo service httpd restart
   Повторно заходим на наш ресурс — теперь он успешно работает.

9. Разбираемся с причиной переполнения файла access_log. Вводим:
   sudo ls -ahl /var/log/httpd
   Смотрим на ситуацию в папке. Там присутствует созданный сегодня
   (2026.06.23) архивный файл log_20260623.tar.gz, который полностью
   перезаписывается каждые 1-2 минуты, и его размер уже составляет
   987 Мб, что в 2 раза больше вчерашнего архива log_20260622.tar.gz.

   Есть предположение, что запущено периодическое выполнение задания.
   Решено посмотреть в файл crontab с помощью команды:
   sudo crontab -l
   В файле crontab обнаруживается следующая строка задания:
   * * * * * tar -czf /var/log/httpd/log_$(date +\%Y\%m\%d).tar.gz -C /var/log/httpd .

   Это означает, что каждую минуту создаётся архив с содержимым каталога
   /var/log/httpd. Проблема в том, что архив создаётся внутри того же
   каталога, который архивируется, поэтому со временем старый архив
   попадает внутрь нового. Обычно архивы складывают в другой каталог.

10. Принимается решение остановить это циклическое задание.
    Для этого запустили команду редактирования крон-заданий:
    sudo crontab -e
    и закомментировали проблемную строку планировщика.

11. Настройка нормального режима backup для лог-файлов.
    Решено написать скрипт, в котором будет производиться:
    - бэкап лог-файлов, остановка веб-сервера, удаление старых логов,
    - новый запуск веб-сервера (он автоматически создаст чистые логи).

    Перед созданием скрипта предварительно удаляем в папке все старые
    архивные файлы: sudo rm -f /var/log/httpd/*.tar.gz
    Создаем скрипт backup_logs.sh в домашней директории ec2-user.

    Код скрипта:
    -----------------------------------------------------------------
    #!/bin/bash 
    	# Каталог с логами Apache, который будет архивироваться     
    LOG_DIR="/var/log/httpd"    
    	# Каталог для хранения архивов 
    BACKUP_DIR="/home/ec2-user/Backup_httpd" 

    # Удалять архивы старше 3 дней
    MAX_BACKUP=3  

    	# Получить текущую дату и время (например: 20260623-14:30:15)
    DATE=$(date '+%Y%m%d-%T')  
    	# Сформировать полное имя архива
    ARCHIVE="$BACKUP_DIR"/backup_httpd_logs-"$DATE".tar.gz
                                   
    mkdir -p "$BACKUP_DIR"
    
    # Создать gzip-архив всех файлов из каталога логов
    tar -czf "$ARCHIVE" "$LOG_DIR"/*

    systemctl stop httpd.service  # Остановить службу Apache (httpd)
    rm -rf "$LOG_DIR"/*           # Удалить все файлы из каталога логов
    systemctl start httpd.service # Запустить службу Apache снова

    # Найти архивы старше 3 дней и удалить их
    find "$BACKUP_DIR" -type f -name "*.tar.gz" -mtime +"$MAX_BACKUP" -exec rm {} \;
    -----------------------------------------------------------------

    Делаем скрипт исполняемым: chmod +x backup_logs.sh
	
    Что делает скрипт целиком
      1. Создаёт архив логов Apache. 
      2. Сохраняет архив в /home/ec2-user/Backup_httpd. 
      3. Останавливает Apache. 
      4. Очищает каталог логов. 
      5. Запускает Apache снова. 
      6. Удаляет старые архивы (старше 3 дней).

12. Открываем crontab командой sudo crontab -e и записываем задание:
    5 3 * * * /home/ec2-user/backup_logs.sh 
    Скрипт запускается каждые сутки в 3 часа 5 минут.


ВЫВОДЫ И ПРИЧИНА ИНЦИДЕНТА:
На сервере было настроено некорректное cron-задание, которое выполнялось
каждую минуту и создавало архив в том же каталоге, который архивировался.
В результате архив бесконечно включал предыдущие версии самого себя, что
привело к быстрому росту файла и заполнению системы на 100%.

Из-за отсутствия свободного места:
- Невозможно было заменить конфигурационный файл LocalSettings.php;
- Возникли проблемы с перезапуском важнейших сервисов;
- Веб-приложение стало полностью недоступным для пользователей.

РЕШЕНИЕ ПРОБЛЕМЫ:
В результате предпринятых шагов работа веб-сервиса восстановлена:
- Удалены критически крупные файлы, освобождено место на диске;
- Восстановлен и скорректирован файл LocalSettings.php;
- Отключено ошибочное cron-задание и настроен новый скрипт бэкапа.

РЕКОМЕНДАЦИИ:
1. Поставить утилиту Logrotate для правильной ротации и сжатия логов.
   Сохранять все файлы бэкапов только в отдельную директорию.
2. Чтобы при перезапуске сервера не менялся публичный IP-адрес в
   переменной $wgServer, рекомендуется использовать Elastic IP от AWS.
